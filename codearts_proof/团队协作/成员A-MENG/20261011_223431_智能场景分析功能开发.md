# 场景体系设计（必须遵守）
采用「大场景 + 小场景 + 视觉属性」三层多标签，维度正交，标签总数受控。

## 数据结构
class SceneTags(BaseModel):
    primary_scene: str | None          # 主大场景，单选，用于排序权重
    scenes: list[str] = []             # 大场景，多选
    sub_scenes: list[str] = []         # 小场景，多选
    visual_attrs: dict[str, str] = {}  # 视觉属性，如 {"time":"night","people":"none"}
    confidence: dict[str, float] = {}  # 标签置信度，0~1

## 标签数量硬约束
- 大场景：6~10 个
- 小场景：总数不超过 60 个
- 视觉属性：每类 2~4 个取值
- 超出白名单的标签一律丢弃或归入 "other"，不允许自由生成

## 场景词典（放在 app/scene/scene_dict.yaml）
scenes:
  nature:
    label: 自然
    children: [beach, mountain, forest, lake, desert, snow]
  city:
    label: 城市
    children: [street, building, night_view, traffic, landmark]
  people:
    label: 人物
    children: [single, group, wedding, party, child]
  life:
    label: 生活
    children: [food, pet, home, office, sport]
  event:
    label: 事件
    children: [festival, celebration, performance, travel, graduation]

visual_attrs:
  time: [day, night, sunrise, sunset]
  people: [none, single, group]
  indoor: [indoor, outdoor]

## 分级推理（避免每张图都跑大模型）
- 第一级：优先复用 Immich 返回的 smartInfo / tags，能映射到词典就直接用
- 第二级：词典未命中时，用轻量 CLIP 做 zero-shot，只判断大场景
- 第三级：只有用户查看单图详情时才补全小场景和视觉属性
- 第一版可以只实现第一级 + 第二级，第三级留 TODO

## 缓存
- 按 asset_id 缓存 SceneTags，使用进程内 LRU（functools.lru_cache 或 cachetools），
  容量默认 2000，可通过环境变量 SCENE_CACHE_SIZE 配置
- 缓存未命中且推理超时，返回 primary_scene=None，不阻塞搜索主链路

## 排序权重按主场景动态调整
在 app/core/ranking.py 增加权重表，不要改动原有 rank_assets 签名：
SCENE_WEIGHTS = {
    "people":  {"alpha": 0.5, "beta": 0.5},
    "nature":  {"alpha": 0.2, "beta": 0.8},
    "event":   {"alpha": 0.4, "beta": 0.6},
    "default": {"alpha": 0.3, "beta": 0.7},
}
搜索时按 primary_scene 取权重，取不到用 default。
原有的 RANKING_ALPHA / RANKING_BETA 环境变量作为 default 的来源。

## 它是干什么的

一句话：**你拿几张图加一句话，它帮你在照片库里"按意思"找相似的照片，并按你的场景自动调整排序。**

具体流程像这样：

1. 你提交一批图片 URL，再给个关键词，比如"海边的日落"。
2. 它先把这些图丢给 **Immich**（一个开源的照片管理软件）做"语义搜索"——不是按文件名匹配，而是按画面意思匹配，所以能找到"夕阳下的沙滩"哪怕文件名叫 `IMG_2034.jpg`。
3. 拿到一批候选照片后，它自己做**二次排序**：综合"拍得新不新鲜"和"跟你的描述像不像"两个维度打分，谁分高谁排前面。
4. 现在新加的功能：给每张结果图**贴场景标签**——比如"自然/海滩/夜景"，然后**按主场景换排序口味**：人物照新旧各占一半权重，自然照更看重语义像不像，事件照介于之间。
5. 最后返回一段结构化 JSON，前端拿去展示。

它还提供一个小接口 `GET /api/v1/scene/dict`，把当前的场景词典吐出来，方便前端做筛选 UI。

## 我觉得最基础的几个缺陷（按重要性排）

1. **第二级场景推理是个空壳。** 真正能"看图认场景"的 CLIP / 华为云图像识别都没接，只留了接口占位。所以一张图如果没有 Immich 自带的标签，就认不出场景——等于这功能现在只对"Immich 已经标过签的图"有效，新图基本白搭。

2. **缓存是进程内的，重启就清空。** 多台机器部署时各存各的，不共享；服务一重启，所有场景标签得重算。

任务写的是"抛 `HTTPException` + detail"，但那样 401 响应体会变成 `{"detail": {...}}`，跟你项目现有的统一错误结构 `{"error": {...}}` 不一致。所以我改用现有的 `AppError` 体系抛 `UnauthorizedError`，走同一个全局异常处理器，输出 `{"error": {"code": "UNAUTHORIZED", "message": "API Key 缺失或不正确", ...}}`——这才是真正的"与现有异常处理器一致"（硬约束 4）。如果你坚持要 `HTTPException` 那种 `{"detail": ...}` 格式，告诉我，我再改。

提供内存 / Redis 两套缓存后端，通过配置切换，Redis 不可用时自动降级。



# 硬约束

1. 不改任何现有业务代码

2. Redis 不可用时降级到内存，不抛异常、不阻塞启动

3. 配置走 Settings，不用 os.getenv

4. 新增依赖仅允许 redis（redis.asyncio）

5. MemoryCache 行为与现有 LRU 一致



# 任务 1：Redis 客户端

新增 app/core/redis_client.py：

- 单例 async Redis 客户端（redis.asyncio）

- lifespan 启停钩子：启动连接、关闭释放

- async health_check() -> bool

- 连接失败只打日志，不阻塞启动



Settings 末尾追加：

- REDIS_ENABLED: bool = False

- REDIS_URL: str = "redis://localhost:6379/0"

- REDIS_TIMEOUT_SECONDS: float = 2.0

- REDIS_KEY_PREFIX: str = "imgsearch:"



# 任务 2：可插拔缓存后端

新增 app/core/cache.py：

- 抽象基类 CacheBackend：get / set / delete，全 async

- MemoryCache：迁移现有 LRU 逻辑，行为一致

- RedisCache：基于 redis.asyncio，值为 JSON 字符串

- 工厂 get_cache() -> CacheBackend：

    REDIS_ENABLED=true 且健康 → RedisCache

    否则 → MemoryCache

- 启动时初始化，注入 app.state



# 任务 3：测试

- MemoryCache 读写、过期、删除

- RedisCache 读写（fakeredis）

- Redis 不可用自动降级

- REDIS_ENABLED=false 使用 MemoryCache

- 现有测试全绿
